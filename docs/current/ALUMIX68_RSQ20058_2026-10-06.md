- `tools/review_redsquare_alumix68_firmware.py` and `..._paths.py` (Unicorn

  vendor read command `0x16` reads RAM `0x20002A9C + offset`; offset `0x200`
  is the live 128-slot LE16 key-depth table (`0x20002C9C`), readable with
  calibration and the selected-key simulation both off. This gives
  independent multi-key depth without held-key loss (the 0x66/0x67 simulation
  stream is selected-key only). Depth unit 0.01 mm, full travel 3.3 mm (the
  configurator shows keyStroke/100 mm).
- Scan map (flash `0x159D2`) joined with the official configurator keyList:
  68 mapped slots, Fn (keyCode 175) = HallJoy Fn.

## Implementation (`redsquare_alumix68_protocol.h`, `redsquare_alumix68_backend.cpp`)

- Exact admission: `0C45:80A2`, vendor collection FF68:61 with 65/65-byte
  reports.
- Firmware gate before any depth read: command `0x12` (flash read) must return
  the exact v1.30 scan map AND a 56-byte window of the command dispatcher code
  (flash `0xE400`). A rebuild that could move the depth table changes that code,
  so the gate fails closed. On mismatch: no connection, `alumix68.firmware_unknown`
  (bit 1 = scan map matched, bit 0 = code matched) and
  `alumix68.firmware_code_head` (compact signature) are logged; the yellow
  notice "Red Square Alumix 68: unrecognized firmware" asks for the log.
- Session: five `0x16` reads (56*4 + 32 bytes) per poll of the depth table,
  read-only; no calibration, no simulation mode, no writes.
- Layout token `redsquare-alumix68` / `RSQ20058-0C45-80A2`; no built-in layout
  yet, so the default 100% layout is shown (yellow does not require a layout).
- Notice flag `RedSquareAlumix68` (268435456), title "Red Square Alumix 68:
  hardware testing incomplete".
- Test: `redsquare_alumix68_protocol_test` (identity, collection, 68 unique
  usages, sentinel slots, request/reply framing, chunk plan, scaling,
  fingerprint self-test) runs in `run_native_backend_checks.py`.

## Collision with AULA MINI 60 HE PRO (found 2026-10-12)

The wired AULA MINI 60 HE PRO (Supported since 1.5.3) has the same USB identity `0C45:80A2`, the
same collection FF68:61 and the same SONiX 0xAA/0x55 transport. Until this fix the Alumix backend
opened every such device, read flash for the firmware fingerprint (neither the scan map nor the
dispatcher code matches an AULA), set "present" and blocked: every MINI 60 HE PRO owner saw the
yellow "Red Square Alumix 68: unrecognized firmware" notice from 2026-10-06 builds on (a Discord user
reported "trouble connecting the app"; the AULA path itself is judged by its own log).

Fix: before any flash read the Alumix backend reads the SONiX device info (`0x10`, 56 bytes, the same
read the AULA backend sends) and skips the device, silently and permanently until a device change,
when it carries VID/PID `0C45:80A2` with manufacturer `0x0166` and product `0x110C` (the identity the
AULA backend requires). It also sends nothing to an interface that another protocol has claimed.
Log: `alumix68.not_alumix_aula_mini60`. A device that does not answer device info is probed as before.
Test: `redsquare_alumix68_protocol_test` (info framing, identity match and mismatches, reply parse).
Validation: `run_native_backend_checks.py --require-compiler` PASS, `build_release.ps1` PASS (all gates); local EXE
SHA-256 `cf61dc38a6f32430bd7839697518eb03bfcfd692a74a81601227332900c126b3`, not published. No MINI 60 or Alumix hardware test.

### Tester log after the first fix (2026-10-12, `HallJoylog.txt`, 1.6.9.0, MINI 60 HE PRO)

The log (bus name `MINI 60 HE PRO`, `0C45:80A2`, interfaces 00..03) still had
`alumix68.firmware_unknown value=0` (neither scan map nor code matched; scan head `0x0101010101010101`)
and no `alumix68.not_alumix_aula_mini60`. The build sent to him (EXE `cf61dc38...`, built 14:06,
log 14:34 local) contains the first fix, so the device-info check did not recognize his unit: his
manufacturer/product values differ from the hard-coded AULA identity (manufacturer `0x0166`, product
`0x110C`; the product value comes from the MCU identification register and can vary by chip batch).
The same mismatch explains why the AULA backend never connected (`aula-mini60-he-pro present=0`).
The log could not show the numbers: AULA wrote `identity_mismatch` without values and only to the
stability trace.

Second fix (local build, EXE SHA-256 `f34f2eac1ea88e0e4888606feaca919ba6b38495c160cd0423069b4aeaefb13b`):
- `aula_mini60_name.h`: `IsMini60ProName` (USB product string, case/space-insensitive "MINI60HEPRO").
- Alumix `Enumerate` reads the product string (control read, no vendor command) and skips a device named
  MINI 60 HE PRO before any probe (`alumix68.skipped_mini60_name`); no notice, no flash reads.
- `Identity(...)` takes `namedMini60Pro`: a `0C45:80A2` unit named MINI 60 HE PRO is accepted when the AULA
  manufacturer `0x0166` and the VID/PID echo match, even if the product register differs.
- Diagnostics in HallJoy.log: `alumix68.device_info value=manufacturer<<16|product detail=vid<<16|pid`;
  AULA `evidence.mini60 descriptor/device_info/identity_mismatch/...` for every MINI60-family device
  (identity_mismatch now carries vid/pid/manufacturer/product/version bytes), each distinct line once, max 48.
- Tests: `aula_mini60_native_model_test` (name helper, relaxed identity limits), run in
  `run_native_backend_checks.py` PASS; `build_release.ps1` PASS. No hardware test; if his manufacturer is not
  `0x0166` the AULA backend still refuses and the new log lines show the real values.
