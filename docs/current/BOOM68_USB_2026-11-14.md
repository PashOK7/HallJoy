[LANGTU configurator](https://langtu.driveall.cn/) lists a separate supplier on
the same VID/PID. Use the exact product name from HID or bus metadata in

both returned BOOM68-USB 1.10. The package contains a SN34F280 image, pinned

The USB hardware descriptor in the image independently matches 0C45:80B5.
The package version is separate from the tester's installed firmware.

## Firmware findings

The firmware dispatcher at D214 copies the request to the reply buffer before
processing. 68 returns that echo. 66/67 toggle a volatile flag and the sole
reviewed FB producer is gated by calibration. The normal scan routine maintains
the calibrated depth cache independently of both flags. GET10 can call the
persistent flash helper to convert an old metadata marker. The BOOM68 client
uses descriptor metadata and never sends GET10.

GET12 supplies the read-only ROM proof and the hardware-to-logical channel map.
GET16 copies the existing calibrated depths for the mapped physical positions.
The prepared firmware replay actually executes both getters. It verifies zero,
67 simultaneous depths, one independent release, shallow values and full
release. Every channel maps one-to-one to the official 67-key ANSI layout,
including Fn. The call trace excludes the flash helper for both getters. The
replay uses modeled scanner RAM and does not measure physical USB, latency,
sensor depth or simultaneous typing. Selected route is LIMITED_ONLY because
the cache retains the firmware's cutoff, filtering and bottom snap, and the
host receives independently timed pages. The review and raw receipt are pinned
in .local/firmware-behavior/boom68-stock110-20261114/. Vendor contents stay local.

## HallJoy integration

First read the immutable code proof and require an unambiguous hardware channel
for every known physical position before using the raw depth offsets. Product or
software version strings never authorize those offsets. Missing or changed ROM
proof and ambiguous channels still reach the documented 68 compatibility trial.
A request echo fails proof. Unknown revisions reaching 68 use provisional units
in the log. The reviewed RAM route uses the firmware switch-axis range, 3.3 or
3.4 mm. It reads bound positions first and rotates through the rest of the matrix
and current axis metadata without a fixed wait or artificial input rate cap.
Reported zeros clear keys. Assignment failures retain factory positions. Duplicate
key aliases remain separate physical channels; geometry-cache exhaustion still
allows sampling. Disconnect and Pause clear publication and drain I/O.

The common Sonix transport owns one session at a time. The existing wired F75
priority over its receiver is retained. A separate simultaneous AULA/BOOM68
session is outside this implementation. Version, remapping and format evidence
are visible in the bounded ordinary log. The revised Sonix evidence records also
fix the AULA truncation observed in the original F75 receiver log.

Use the ordinary HallJoy.exe and Open log after trying normal input. Report
whether several simultaneously held keys return to zero when released. No
configuration or firmware update is needed to try the reviewed stock device.
