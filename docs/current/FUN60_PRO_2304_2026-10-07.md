# MonsGeek FUN60 Pro board 2304 (3151:502D) — 2026-10-07

## Lead

The public fork BoneDrk/HallJoy (found 2026-10-07) carries a workflow that
patches HallJoy 1.6.7 (`a510933`) at build time for one user's FUN60 Pro. Its
notes: the user's 1.6.7 support log repeatedly showed
`rongyuan.identity_pair_rejected` board 2304 on 3151:502D. Only these facts were
used. No code was taken from the fork (HallJoy is dual-licensed; contributions
need the author's consent for the commercial license). The fork's own approach
(require the live keymap to equal the factory map; drop `[`, `'`, `\` because
the user's live map had no standard key there) is not used.

## Evidence (official MonsGeek web driver)

- `https://app.monsgeek.com/js/index.13c08899.js` (unchanged since 2026-09-22,
  SHA-256 `e88543d0...cb96a`, local copy `.local/research/monsgeek-20260922/`):
  `{id:2304,vid:12625,pid:20525,keyLayout:h.Common61_gk06,
  name:"ry5088_akko_fun60pro_1m_8k",displayName:"FUN60 PRO",company:"MonsGeek",
  ...,magnetism:!0}`. Boards 2600 and 2785 (already supported) use the same
  key layout name.
- RY5088 device chunk `https://app.monsgeek.com/js/a0c3a7d8.js` (retrieved
  2026-10-07, SHA-256 `c721ddc0...74e6`, kept local): `case
  "ry5088_akko_fun60pro_1m_8k": return new i8(a)`; `class i8 extends k` holds
  only `defaultMatrix`, `defaultFnMatrix` and `defaultFnMacMatrix`.
- The extraction reproduces the existing profiles exactly (2600 and 2785
  matrices from this chunk equal `profiles.json` byte for byte). Board 2304's
  `defaultMatrix` equals board 2600's in all 128 slots: 61 keys, including
  `[` (slot 68), `'` (69) and `\` (80). Only the Fn layers differ; HallJoy does
  not use them for analog. Same stream parent `k`, so the same commands.
- Conclusion: the fork user's three missing keys were live assignments (a
  remap/profile), not a different board map. HallJoy keeps the factory map
  (physical key identity) and live assignments separately, so all 61 keys stay.

## Implementation

- `kUsbAliases` gains `canonicalBoard`: `{2304, 3151:502D} -> 2600 / 3151:5029`.
  Existing aliases keep their own board. Same FUN60 Pro profile, product
  `RY1B-2600` (automatic layout), 4 mm provisional range, yellow notice.
- `rongyuan_stream_backend.cpp`: the session stores the board the keyboard
  reports; telemetry resolves the model with it (an alias board would otherwise
  not be found) and `rongyuan.connected` / `start_failed` log it (2304).
- Evidence: `docs/research/usb-identity-audit/approved-aliases.json` (record,
  class text, matrix SHA-256, `canonical_board`) and `catalog-comparison.json`
  (approved difference); `tools/audit_keyboard_identities.py` checks the
  canonical board's matrix like every alias. `KEYBOARD_IDENTITY_AUDIT=PASS
  aliases=4`.
- Test: `rongyuan_stream_protocol_test` — 2304/502D resolves to the 2600 model
  with `[ ' \` present; 2304 on other PIDs and 2305 are rejected; aliases map to
  their canonical board.
- Support status: FUN60 Pro stays Implemented (yellow); README, notice catalog
  and the Sheet row are per model and unchanged; SUPPORTED_HARDWARE lists board
  2304. No physical test.
