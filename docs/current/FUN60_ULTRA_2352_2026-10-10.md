## Vendor map: 2352 is not 2600 with a different name

Both driver classes extend the same stream parent `k`. Their `defaultMatrix` arrays
(128 slots x 4 bytes) differ in five consecutive slots (59 to 83); the other 123 slots match:

| Slot | FUN60 PRO 2600 | FUN60 Ultra 2352 |
|---|---|---|
| 59 | empty | RAlt (230) |
| 65 | RAlt (230) | bytes 10,1 (same bytes as 2600's slot 71) |
| 71 | bytes 10,1 | Menu (101) |
| 77 | Menu (101) | RCtrl (228) |
| 83 | RCtrl (228) | empty |

So the bottom-right keys sit one slot apart. Reusing the 2600 matrix for 2352 would send
RAlt, Menu and RCtrl analog values to the wrong keys. The board needs its own matrix.

## Attack Shark probe defect (fixed in this change)

`SharkDiagnostic_Start` runs in ordinary builds. After an identity rejection, the
capture loop slept 3 s and probed again, indefinitely. The tester log shows about
15 cycles in 45 s: 3 identity queries (0x8F, twice each) per cycle, 690 log lines.

Fix in `attackshark_pro_diagnostic.cpp`:
- An identity-only pass is retried 3 times per device topology, which covers replies
  that arrive late after plug-in.
- After that, the probe waits for a device change (`SharkDiagnostic_DeviceChanged`)
  instead of re-probing.
- Open failures ("device busy", close the vendor driver) keep the 3 s retry, so a
  device that frees up is still picked up.
- The new event `identity_waiting_for_change` is mapped to `shark.identity_waiting`
  and covered by the self-test.

  shows no VID 0x38EE and no 3151:5030 device. The only MonsGeek keyboard is 3151:5029,
  board 2352 (the Hall FUN60 Ultra).
- Vendor identity of the TMR: board 3853 (`ry5088_akko_fun60_ultra_tmr_3m_8k_8k`), USB
  38EE:0001. The flasher data has no entry for 3853. Board 3269 (Shine68) uses the same
  38EE:0001 identity, so the PID does not identify the model on its own.
- HallJoy has no 38EE identity: `mg::Candidate` in `rongyuan_stream_protocol.h` never
  matches it, so the RY1B enumerator skips the device even when it is plugged in.
- Matrix (official class `R8`): it differs from FUN60 PRO 2600 in slots 11, 17, 23, 59, 65,
  71, 77, 83, and from board 2352 in slots 11, 17, 23 only. Each board needs its own map.
- Class parent: `R8` extends the same base `t` as `k`, but not `k` itself. Whether the
  members that `k` adds change the magnetism stream is not known.
- Other TMR boards already in the RY1B table are on 3151:5030 (M1 V5 TMR 2949, GamaKay TK75
  TMR 3590/3591, Womier SK75 TMR 2518/3804). They do not show the 38EE family.

Missing for the TMR, in order: a log taken with the TMR connected (its HID line gives the
real VID/PID), the identity in HallJoy's tables, the 3853 map from the official class, and
a stream capture on that identity. No firmware for 3853 is on disk; the vendor API has no
record for it (`Record not found`).

## Tester log 2 (HallJoy (1).log, build d77528f9) and fix

- `rongyuan.enumerate value=7 detail=1`, `enumerate_pairing value=1 detail=1`: control and
  report-5 input collections paired.
- `rongyuan.admission_failed value=3 error=121`: identity proof PASSED (board 2352 admitted),
  then the assignments read (0x84/0x8A) failed with ERROR_SEM_TIMEOUT from the HID stack about
  5 s later (USB control timeout), not HallJoy's own 50 ms timeout.
- Then the Attack Shark probe opened the same collection exclusively and kept probing board
  2352 (3 passes, `set_feature_failed 121` once). While it held the handle the RY1B scan could
  not read its metadata (`enumerate value=6 detail=0`, pairing 0) and the worker slept with an
  INFINITE wait (no candidates). Releasing a handle raises no device change, so RY1B never
  looked again: no analog for the rest of the session.

Fixes (build 04643a7c15e5bad10cd5d18c52f97c7c3ad7030f33776ad6d9262fc041e305c7):
1. RY1B feature exchanges follow the manufacturer driver timing (`commonMsg`: `sendMsg` waits
   10 ms before SET_FEATURE, `readMsg` 10 ms before GET_FEATURE); HallJoy read immediately and
   polled every 1 ms. Reply window 100 ms, polled every 10 ms. Enable/disable 0x1B use the same
   send gap.
2. RY1B worker: a visible keyboard whose pair is not usable is rescanned every 2 s; identity
   rejections are retried 3 times per device topology, then wait for a device change
   (`rongyuan.identity_waiting`), instead of re-querying an unknown board every second.
3. Attack Shark probe: an identity that the RY1B table admits on this VID/PID makes the probe
   stop at once and wait for a device change (`shark.identity_stream_owned`).
4. Log: `rongyuan.admission_command value=<last command> detail=<Win32 error>`.

Native suite PASS, build_release.ps1 PASS.
