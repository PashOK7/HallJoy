## Wireless feasibility follow-up — 2026-11-05

Owner asks whether 2.4GHz is possible. Current result: **not implemented, with
concrete protocol paths to investigate; neither working radio analog nor its
impossibility has been established**. The existing EXE still requires wired USB.
Older statements that no RongYuan receiver analog exists describe HallJoy's
missing receiver admission, not an exhaustive firmware/radio analysis.

The pinned official v4 main bundle (SHA919b1049...) contains a dongle transport:
- ___dongleSend24GDeviceByF6 selects keyboard with F6/0A.
- ___dongleCheck24GStatusByF7 queries F7 ready/online/read/write status.
- ___dongleNoticeReadByFc sends FC before reading the remote response.
- Dongle ___getNormalID sends read-only8F through that transport, rather than
  inferring the remote model from the shared receiver's VID/PID.
- Class m4.sendMsg/readMsg routes connect=24g through dongle.sendMsg/readMsg;
  ordinary feature requests are not automatically sent directly to the receiver.

Exact V4S parent07c90958.js (SHA7982b093...) implements1B stream control and
E5/FE/01/page current-depth table reads. Neither of those method bodies contains
an explicit USB-only transport guard. This establishes client-side command paths,
NOT that the remote firmware forwards per-key stream reports or returns fresh
multi-key depth over RF. UI availability was not exhaustively traced.

Two candidates remain: tunnel1B enable/disable and verify asynchronous depth
reports from the receiver, or tunnel read-only E5/FE depth snapshots. The latter
may be too slow: vendor dongle helpers wait100ms between ready polls, and the
full table needs4 pages. Those software waits do not establish a physical radio
latency floor or prove they can safely be removed. No latency promise is made.

A bounded tester investigation must verify remote board3793, actual depth across
several simultaneously held keys, releases, freshness, ordinary typing, cleanup
and configurator contention. A readable settings channel alone proves none of
these. Firmware changes are only a possibility if stock depth routes fail, not
a known requirement. No receiver commands, firmware writes, runtime changes,
new EXE, support promotion or Sheet status changes were made in this follow-up.
