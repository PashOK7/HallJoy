# MG75 Max Fn and Pro protocol correction

> Superseded Pro family conclusion: see [firmware and SDK review](MG75_PRO_V2_REVIEW_2026-09-19.md). Independent Pro travel reads are confirmed in SparkLink V1 SDK and firmware; runtime integration remains pending.

## Confirmed evidence

The pinned official IROK client separates MG75 Pro (JingTaiMg75 within JingTai V1, ID 137919531015) and MG75 Max (JingTai V2, ID 480642345). Their layouts share a visual key order, not a demonstrated analog transport.

Official firmware articles https://api.mall.irok.cn/v3/news/90 and /75 supplied Max 1.1.3.0 and Pro 1.1.0. They were downloaded as data, without running an updater. The Pro updater embeds multiple images: only the MG75_PRO image was selected for the model finding, with an exact embedded SHA-256 match. Hashes and the Max matrix are recorded in ../research/MG75_FN_EVIDENCE_2026-09-19.json. Original downloads stay under .local/research/irok-mg75-fn/.

Max: the Windows factory matrix at file offset 0x1B87C has 6x21 cells, 81 nonzero assignments. Its complete HID multiset equals the layout, after converting Fn action F101 to HallJoy 409. Fn is row 5, column 11. The official SDK reads 21 little-endian 16-bit layout entries with 03/01 and row travel with 04/03/01; the client iterates all row cells, including Fn. No calibration command is involved. This establishes the format and missing publication path, not a physical keyboard test.

Pro: the official _It/CMt path sends 5C 04 12 checksum type half FF FF. Its KMt map assigns telemetry index 146 to vendor key 1 (Fn). Calibration is a separate command. This is not the Max row protocol. Downloading the image is not a completed firmware-disassembly or USB-framing proof. A matching active MG75 Pro backend is not established in this build. The former README family assumption was removed; the manual layout remains. A real Pro implementation requires its own exact admission, transport framing and publication work, rather than enabling frozen NA87 Pro code or applying a Max decoder.

## Implementation

SparkLink now decodes only the confirmed F101 extended action as Fn 409. Other unknown extended actions stay unmapped; code 1 is not guessed to be Fn. Matrix identities and published values use a wide enough domain through normalization, row aggregation, expiry, ownership, logging and V2 snapshots. Existing byte-domain callers retain their 256-entry default. Extended Fn snapshots use UapExtendedKey, never a fake USB keyboard usage. Partial row snapshots remain marked partial.

No new probe, device write, calibration or digital-depth fallback was added. No Pro or frozen protocol was enabled. No live-device or visual test was performed.
