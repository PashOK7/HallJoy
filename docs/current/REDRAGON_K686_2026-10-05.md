## Tester log 56 (2026-10-05 17:38 UTC) and "buttons are sticking"

- Log: `aula-w669-adaptive connected 2E3C:C365`, 97 mapped keys (US variant:
  98 positions incl. Fn), 230 live events in ~2.5 min, 0 failures.
- Tester (kawaman7): "the controller sticks are working correctly, but the
  buttons are sticking". Status stays Implemented (yellow).
- Wire format matches the official client exactly (one event per report: row,
  column, LE travel). K673 BR physically sent an explicit zero on every
  release (72 presses / 72 zero events). Most likely K686 cause: its firmware
  stops reporting inside its top dead zone / below its minimum actuation, so a
  release can end at a small positive value: inside a stick deadzone, but above
  a button threshold. Not proven (the ordinary log had only a total count).
- Changes:
  - live travel at or below the keyboard's own minimum actuation (21/04 byte
    the official client reads as `minTriggerTravelRaw`) is published as 0; a
    value of 20% of the range or more is treated as implausible and ignored;
  - support log, aggregate only: `w669.travel_config` = max << 16 | unit << 8 |
    minimum; `w669.release` every 10 s when changed and at session end =
    presses (0 -> positive) << 44 | releases (positive -> 0) << 24 |
    keys left positive for >= 1 s << 16 | their largest value in permille << 4 |
    floored events (max 15).
- Validation: protocol test covers the floor; `build_release.ps1`, diagnostics
  gate and native suite PASS. EXE SHA-256
  `a068ebe00b5a65f2d6599c4c5a02bbfb446730774561d69cd664e0e35c38da3b`.
- Next log: presses vs releases and the residual value show whether the floor
  is enough or a dead-band read (official command 38) is needed.

## Tester log 57 (2026-10-06 00:43 UTC): release fixed; new report about sticks

- Build with the release floor (`w669.release` present). 38 aggregates over
  ~6 min: presses 11032 -> 11669, releases equal to presses (a difference of at
  most 2 = keys held at that moment), 0 keys left with a residual value,
  floored events >= 15 (the floor is in use). 254,200 updates, 0 failures.
  The sticking of the buttons is gone in the log.
- New tester report: "the analog sticks (L & R) work in reverse, left is
  right, up is down, and the triggers seem constantly pressed"; the tester
  says they struggled to configure the controller.
- Not a W669 symptom: every key returns to 0, and the gamepad mapping is
  generic. All three symptoms match an inverted curve (global "Invert" or the
  per-key Invert in Configuration, `x = 1 - x`): bound keys output full value
  at rest (triggers held), and pressing one direction lowers it below the
  opposite one (stick moves the other way). A DirectInput view of an XInput
  pad (Y down, both triggers on one centred axis) explains two of three. The
  log could not tell; the configuration was not logged.
- Change: every snapshot now writes `input.config` (aggregate counts only, see
  SUPPORT_DIAGNOSTICS_CONTRACT.md). Status stays Implemented (yellow) until
  the tester confirms the controller works.

  Invert is off; the inverted-curve explanation was a guess, and the aggregate
