  So VID:PID alone does not identify the model on this platform; RongYuan software tells boards apart by the board id
  the keyboard reports.
- The USB product string is `RT80`, and only board 2068 carries that name on this PID. Together with the owner's report, the
  keyboard is the YUNZII RT80 (or an identical rebadge of the same board). The board id itself is not in this log; a
  read-only device-info query would confirm 2068 exactly.
- No collision with implemented models: the implemented AIM1 MATATAKI (US) revisions are boards 2939/3026 on `3151:5029`.

## Protocol

Board 2068 inherits the legacy `CommonKbYc500` parent (`2e81aae0.js`), not the reviewed RongYuan stream parent. The
2026-09-24 review (NEXT_PROTOCOL_REVIEW_2026-09-24.md, "Legacy RongYuan CommonKbYc500") already put RT75/RT80/RT68 on hold.
Re-checked for this log:
- The only live-analog path is `setKeyMagnetismReport` = command `0x1B` (FEA_CMD_SET_MAGNETISM_REPOR) with 1/0, used only by the
  configurator's "Simulation Test" tab (`模拟测试`).
- The configurator's own warning for that tab: when simulation testing is on, the keyboard may not work until it is stopped.
- The tab shows one value (`模拟测试数值`), not per-key travel; the earlier review found the UI reads a single scalar. No
  per-key identity in the live data is established.
- `0x1C`/`0x1E` are calibration commands and must not be used; `0x9C`/`0x9E` read calibration values only.

Conclusion: no usable per-key analog interface is established for the RT80. A one-value test mode that may stop typing does
not meet HallJoy's requirements. The next step would be a probe build like the MADE68 Air one (switch `0x1B` on, log raw
frames while keys are pressed, switch it off), which needs the owner's decision because the vendor warns typing may stop
during the test.

## Follow-up the same day: firmware, calibration getters, the tester's other keyboards

**Firmware (owner asked for a fresh look).** The official RongYuan update service answered `get_fw_version` for board 2068:
`v104_rfv202` (YUNZII, lowest app 2.1.73, uploaded 2024-11-21). Boards 2573 and 1753 (RT75): `Record not found`.
Package `fw_upgrade_file/2068_v104_rfv202` (zip, SHA-256 `b77aa2d6e1bb62050e1b8f86ca79740adb81a560a3ada4c1561f42231f628aec`)
is kept local only in `.local/research/yunzii-rt80-20261015/` (vendor firmware, no redistribution permission). It holds
`firmwareFile.bin` (35,684 bytes, RISC-V USB bridge; contains USB descriptor 3151:4035 and product string RT80) and
`firmwareRFFile.bin` (289,088 bytes, ARM application MCU, flash base 0x01000000). Static review completed 2026-10-15.

**ARM firmware command dispatch — confirmed by static analysis (Capstone, 2026-10-15).** Two switch tables share the
dispatcher function at file offset 0x22632:
- Table A (commands 0x00–0x40, base LR 0x1bea7, size 65): covers `0x1B` (idx 27 → 0x1c034), `0x1C` (idx 28), `0x1E` (idx 30).
- Table B (commands 0x90–0x9F, base LR 0x1bf49, size 16): covers `0x9C` (idx 12 → 0x1c040), `0x9E` (idx 14 → 0x1c04c).

All four commands are dispatched to real handlers with no mode gate. The general binary-search dispatcher (0x1be94)
handles commands 0x41, 0x42, 0x65, 0x7E–0x8F, 0xa5, 0xad, 0xae, 0xb1, 0xc0, 0xc1, 0xe5 separately.

**Command 0x1B (setKeyMagnetismReport / simulation test), handler 0x189ee:** reads the ON/OFF byte from the HID request
and stores it in one field of a runtime struct. That is the entire handler. It does not return analog data and does not
configure any streaming. The vendor's own UI (Simulation Test tab) shows a **single scalar** `模拟测试数值`, not per-key
travel; the keyboard may not work (typing stops) while the flag is on. **0x1B is not a per-key analog path.**

**Commands 0x9C / 0x9E (calibration getters), handlers 0x18a6c / 0x18ac4:** both handlers have the same structure:
read a `page` byte from the HID request (0–3), compute `cal_data_SRAM_base + page × 64 + per_type_offset`, copy 64 bytes
(= 32 × uint16) to the response buffer, then if page == 3 clear 4 padding bytes. Source base for 0x9C offset = 0x1d2a,
for 0x9E offset = 0x1f22 (different slices of the same SRAM region). **No mode gate.** These commands always respond.
However, the 64-byte pages contain CALMAX (0x9C) and CALMIN (0x9E) — the highest and lowest ADC values recorded *during
calibration*. They are static between calibrations; they do not update with key travel in normal operation. A probe
could confirm this empirically, but combining static bounds with no live-position command yields no usable analog depth.

**Conclusion (firmware-confirmed):** No path exists in the RT80 firmware that streams current per-key travel depth in a
way compatible with HallJoy's requirements. 0x9C/0x9E respond unconditionally but return static calibration bounds.
0x1B toggles a single flag; its associated mode provides only one scalar and may stop typing. Status remains
`Research incomplete`; a probe build would only confirm the CALMAX/CALMIN static nature and cannot unblock support.
