# ND75: исправления после ревью, 2026-09-13

Владелец попросил продолжить работу после [ревью](IROK_ND75_REVIEW_2026-09-13.md).
Этот документ описывает последующие правки, поэтому замечания ревью о неизменённом
runtime и неверной команде относятся к сохранённому состоянию до этих правок.

## Сделано

- В protocol builders используется общий wire opcode0x21 для прямого HID.
  Ненужное разделение host29/device21 удалено: host29 относится к входу SDK,
  которого этот backend не использует.
- Добавлен TryTravelToMilli: диапазон0..40 преобразуется в0..1000;
  остальные значения отклоняются. Publish считает ошибку и возвращается
  до изменения опубликованного состояния. Последнее достоверное значение
  сохраняется; недостоверный пакет не превращается ни в нажатие, ни в отпускание.
- Raw decoder сохраняет исходный байт для диагностики. Диагностические min/max
  и число полученных сообщений остаются сырыми; счётчики нажатий/отпусканий
  и уникальных нажатых клавиш учитывают только допустимые значения.
- Добавлены полные64-байтовые эталоны capability/subscription/unsubscribe,
  полученные из подтверждённого wire format, реальная форма live event с byte5=3,
  отпускание и проверка всех256 значений travel. Проверки привязаны к формату
  прошивки, а не только к константам реализации.
- Static audit больше не выдаёт наличие PublishOwnership за доказательство
  достоверности состояния. Поведение конвертера проверяет C++ test;
  возврат до публикации дополнительно проверен ревью кода.

## Нерешённое состояние клавиш

Проблему потери событий нельзя исправить одним parser или таймаутом. Из ранее
подтверждённой перезаписи последнего события следует неразличимость двух случаев:

| Состояние первой клавиши | Изменение второй | Наблюдаемый ответ |
|---|---|---|
| Первая остаётся удерживаемой | Вторая меняет глубину | Новая глубина второй |
| Первая отпущена, её событие вытеснено | Вторая меняет глубину | Та же новая глубина второй |

Это вывод из подтверждённого механизма, не новый аппаратный тест.
Получив одинаковые сообщения, HallJoy не может определить правильную глубину
первой клавиши. Частота чтения USB сама по себе не восстанавливает событие,
вытесненное внутри одного scanner pass. Повторная подписка не является снимком
глубин. Обычный цифровой key-up тоже не даёт независимую аналоговую глубину:
порог цифрового отпускания нельзя приравнивать к физическому нулю.

Поэтому PublishOwnership и хранение последнего состояния не объявлены исправленными.
Для всего диапазона клавиш нужен достоверный снимок/опрос состояния либо
подтверждённая доставка всех изменений. Частичный сохранённый результат52/81
остаётся частичным; на этом этапе он не внедряется. Обычная NA87 всё ещё требует
собственной firmware/capture; семейство Witmod/M484 не доказывает совместимость.
