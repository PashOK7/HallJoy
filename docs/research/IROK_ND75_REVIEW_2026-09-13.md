## Находки в коде

1. **P1 — неверный opcode прямого HID.** `irok_nd75_protocol.h:15` задаёт
   `kHostAnalogCommand=0x29`; builders в `irok_nd75_protocol.cpp:49,58,67`
   используют его для прямой отправки backend. Реальный Witmod SDK переводит
   0x29 в 0x21 перед HID; firmware dispatcher отвергает raw 0x29.
   Повторно подтверждено отдельной эмуляцией SDK и штатного dispatcher.
   Это мешает capability admission ещё до рабочей подписки.
   Unit test закрепляет 0x29 и потому проходит при неправильном wire format.
   Нужное исправление: разделить SDK input и wire command, проверить wire21
   независимыми эталонными сообщениями. Одной этой правки недостаточно для поддержки.
2. **P1 — нет достоверного полного состояния клавиш.**
   `irok_nd75_backend.cpp:520` обнуляет значения, затем объявляет всю карту
   обслуживаемой (`PublishOwnership`) перед отправкой подписки. Начального
   снимка глубин нет. В ветке timeout (`:571`) старые значения остаются.
   Повторная полная эмуляция scanner подтвердила: изменение одной клавиши
   может вытеснить отпускание другой до отправки ответа. Потерянный release
   способен оставить опубликованное ненулевое значение до следующего события
   этой клавиши либо очистки сессии. Клавиша, удерживаемая до подключения,
   также не получает достоверного начального значения из одной подписки.
   Обнуление по таймеру не решает задачу: оно путает неподвижное удержание
   с потерянным отпусканием. Нужен подтверждённый источник текущего состояния.
3. **P2 — значение за пределами диапазона публикуется как полное нажатие.**
   `DecodeLiveEvent` (`irok_nd75_protocol.cpp:161`) принимает travel255;
   `Publish` (`irok_nd75_backend.cpp:487`) увеличивает счётчик, но продолжает
   публикацию через `ToMilli`, получая1000. Отдельный C++ probe подтвердил это.
   Для рабочего ввода нужен отказ от публикации недостоверного значения
   с сохранением диагностического учёта. Само насыщение в ToMilli — не валидация.

Штатный static audit тоже PASS: он проверяет наличие конструкций исходника.
Его строки про «asymmetric capability» и «authoritative immediately» не служат
доказательством соответствия firmware или корректного состояния всей клавиатуры.
Неиспользуемый helper проверки V1 не является действующим firmware gate.

## Исправления исследовательской проверки

В `nd75_serializer_coverage.py` состояние serializer bit18 записывалось
по неверному адресу. Из инструкций f2ee/f302 и literal f484 следует адрес
20000d3f. Исправлены fixture и проверка посещения ветки f312 только при state1.
Теперь выполняются38 сценариев для20 непустых serializer entry points.
Полная RAM и return каждого сценария совпадают с отдельным запуском без hooks.

У bit18/state1 обнаружена ещё одна проблема instrumentation, аналогичная
известной bit21/state8: MEM_READ hook меняет результат эмуляции.
Эти два сценария проходят без read hook; их источники проверены статически.
Итого36 сценариев имеют read trace, два — исполнение и статический разбор.
Старый JSON сохранён, новый: `nd75-serializer-coverage-reviewed.json`.
Это выбранные состояния, а не перебор всех аргументов и всех путей firmware.

## Уточнение прежнего результата по глубинам

Прежний общий вывод «альтернативного чтения нет» был слишком широким.
Ранее сохранённый частичный эксперимент показывает повторяемое чтение
независимых W/A/S/D, включая W=0 при движении A и удержании S/D, в эмуляции
одной зафиксированной ND75 firmware. Он использовал нестандартное поведение
чтения настроек; это не штатный API и не готовый backend.
На текущем этапе этот эксперимент не повторялся; пересчитано только покрытие
из сохранённого JSON и существующей FactoryMap.

Охват:82 из132 логических слотов;52 из81 непустой позиции карты HallJoy.
Число81 включает внутреннюю Fn, это не81 обычная HID-клавиша.
29 позиций остаются вне этого способа; среди них Esc, E/R/T, F/G/H, Enter,
левый Shift. Поэтому даже сохранённый результат не доказывает полный аналог.
Названия `physical_pointer_slots` в исходном JSON ошибочны: это логические
слоты, их нельзя выдавать за132 физические клавиши. Исходный JSON сохранён
для прослеживаемости; отдельная поправка — `saved-coverage-review.json`.

## Вывод и оставшиеся условия

ND75 действительно хранит независимые глубины; штатная доставка событий
может терять изменения и отпускания. Частичный сохранённый результат по WASD
уточняет возможности одной firmware, но не делает ND75 готовой к использованию.
Обычная NA87 относится к той же ветке Witmod/M484 по официальному каталогу;
её собственная firmware или capture по-прежнему отсутствуют. Переносить
результаты ND75 на неё как доказанную поддержку нельзя.

До включения backend обязательны исправление wire format и range handling,
замена самоподтверждающих тестов эталонами протокола и решение полноты/свежести
состояния. Последнее остаётся техническим блокером; запуск HallJoy его не снимает.
Нельзя объявлять всё пространство возможных firmware-путей исчерпанным.
Pro остаётся замороженным; продолжение приостановленных экспериментов не входит
в текущий этап. Это завершённое ревью, а не готовность к аппаратному релизному тесту.
