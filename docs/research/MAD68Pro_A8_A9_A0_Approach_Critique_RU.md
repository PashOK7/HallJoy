# Критический разбор подхода `A9 → A8 → A9 → A0` для MAD 68 Pro R

## Назначение

Этот документ — запрос на независимую проверку реализации, которая:

1. отправляет `A9`;
2. отправляет `A8`;
3. сразу отправляет второй `A9`;
4. после этого ожидает постоянный поток `A0`;
5. считает, что цифровая клавиатура восстановлена, а аналоговая телеметрия остаётся активной.

По повторному статическому анализу прошивки такая модель содержит несколько критических противоречий. Ниже приведены конкретные вопросы, которые можно подтвердить или опровергнуть кодом прошивки и аппаратным логом.

---

## 1. Главное противоречие машины состояний

### `A8`

Обработчик opcode `A8` расположен около `0x000063F8` и вызывает функцию около `0x0000530E`.

По текущему разбору она:

- устанавливает bit `0x08` в общем mode byte `0x2000580B`;
- записывает число полных проходов `3`;
- помечает 72 позиции как требующие отправки;
- запускает состояние планировщика `A0`.

Условие активности планировщика:

```text
(mode_byte & 0x08) != 0
```

### `A9`

Обработчик opcode `A9` расположен около `0x000063E0`.

По текущему разбору он делает:

```text
mode_byte = 0
memset(change_flags, 0, 72)
```

То есть `A9` очищает тот же bit, который разрешает отправку `A0`.

### Планировщик `A0`

Планировщик расположен около `0x0000A0A8` и перед каждым новым пакетом повторно проверяет:

```text
(mode_byte & 0x08) != 0
```

### Следствие

Последовательность:

```text
A9 → A8 → A9
```

должна выглядеть так:

```text
первый A9: mode = 0
A8:       mode |= 0x08, A0 разрешён
второй A9: mode = 0, A0 снова запрещён
```

Поэтому устойчивый поток `A0` после финального `A9` статически не объясняется.

Возможен короткий race, если scheduler успеет сформировать один пакет между `A8` и `A9`, но такой race:

- не может надёжно дать 68/68 или 72/72 позиций;
- не может поддерживать постоянный поток;
- не годится как production-механизм.

**Просьба:** показать точный control flow, отдельный persistent flag либо ошибку в этом разборе.

---

## 2. Временное ограничение против полного snapshot

В `A0` scheduler найден limiter:

```text
15 timer ticks между пакетами
```

По структуре прошивки timer похож на миллисекундный. Тогда приблизительно:

```text
1 пакет A0         ≈ 15 мс
72 slot            ≈ 1,08 с на проход
3 стартовых прохода ≈ 3,24 с
```

`A8` записывает три прохода. Следовательно, чтобы получить полный стартовый набор, `A8` должен оставаться активным не меньше примерно 1,08 секунды, а для всех трёх проходов — около 3,24 секунды.

Если второй `A9` отправляется сразу после ACK на `A8`, полный набор не должен успеть сформироваться.

**Просьба:** указать реальное время между `A8` и финальным `A9`, а также timestamps всех полученных `A0`.

---

## 3. ACK команды нельзя считать Hall-телеметрией

Нужно строго различать:

```text
ACK A8/A9 ≠ asynchronous A0 Hall report
```

Аппаратный лог должен показывать после финального `A9` именно пакеты:

```text
wire byte 0 = A0
```

Причём они должны продолжаться несколько секунд и отражать новые физические нажатия, сделанные уже после того, как очередь старых пакетов опустела.

Нужны:

- TX `A9/A8/A9` с полным hex;
- RX ACK с timestamps;
- RX `A0` с полным hex;
- количество `A0` до и после финального `A9`;
- длительность наблюдения после финального `A9`.

---

## 4. Возможна путаница двух разных `A0`

В vendor jump table есть host opcode `0xA0`, который выполняет обычное чтение config/static области.

Одновременно асинхронный Hall report тоже имеет marker `0xA0`.

Это разные сущности:

```text
host command opcode A0
asynchronous Hall report marker A0
```

Настоящий Hall report должен:

- формироваться builder-функцией около `0x00009F30`;
- содержать физический 3-байтовый descriptor в bytes `1..3`;
- содержать live Hall value в bytes `4..5`;
- приходить без отдельного host request для каждого key packet.

**Просьба:** подтвердить, что parser не принимает ответ на host opcode `A0` за асинхронный Hall packet.

---

## 5. Очереди USB/HID могут создать ложное впечатление потока после `A9`

После того как генерация прекращена, старые пакеты могут оставаться:

- в firmware staging buffer;
- в endpoint FIFO;
- в USB controller;
- в Windows HID queue;
- в завершённых overlapped reads.

Поэтому несколько `A0`, прочитанных после финального `A9`, ещё не доказывают, что они были сформированы после него.

### Проверяющий тест

```text
A9
очистить input queue
A8
держать A8 active 4 секунды
A9
2 секунды ничего не нажимать и дочитать очередь
только после этого медленно нажимать W ещё 3 секунды
```

Критический вопрос:

```text
появятся ли новые W-correlated A0 после двухсекундного drain уже после A9?
```

Если нет — финальный `A9` действительно выключает поток.

---

## 6. Конфликт между аналогом и штатными буквами

В Hall scan code найдены проверки общего mode byte примерно около:

```text
0x0000AA6A
0x0000AB72
```

При ненулевом mode выполнение:

- уходит из normal digital-state path;
- пропускает часть normal actuation/rapid-trigger обработки.

Это создаёт конфликт:

```text
A8 active  → A0 есть, normal digital вероятно подавлен или изменён
A9 applied → normal digital восстановлен, но A0 gate очищен
```

Если реализация утверждает одновременную работу нормальных букв и `A0`, необходимо показать:

- какой отдельный telemetry flag остаётся после `A9`;
- где он устанавливается;
- почему `A0` scheduler продолжает работу при `mode=0`;
- почему digital scan идёт по normal branch.

В текущем аудите отдельный persistent telemetry flag не найден.

---

## 7. Заявление `68/68` требует проверки свежести

Если HallJoy сообщает `68/68`, нужно уточнить:

1. Эти descriptors были сформированы после финального `A9` или до него?
2. За сколько времени они собраны?
3. Input queue очищалась перед тестом?
4. Старые packets не учитывались повторно?
5. Есть ли sequence number либо иной признак свежести?
6. Отделяется ли host receive timestamp от firmware generation time?
7. Не были ли 68 packets накоплены за время, пока `A8` ещё оставался активным?

Host timestamp чтения сам по себе не доказывает момент формирования пакета в клавиатуре.

---

## 8. Даже рабочий stock `A8/A0` может быть слишком медленным

Текущий статический вывод:

```text
одна физическая позиция на один 64-байтовый packet
не чаще одного packet примерно на 15 timer ticks
```

Оценка при 1 ms tick:

```text
одна движущаяся клавиша        до ~66,7 Гц
четыре активные клавиши        в среднем до ~16,7 Гц на клавишу
полный проход 72 slot          минимум ~1,08 с
```

Это приемлемо для диагностики, но может быть недостаточно для качественного аналогового WASD.

Нужно измерить:

- aggregate packets/s;
- частоту W/A/S/D отдельно;
- worst-case latency;
- jitter;
- packet loss;
- поведение при одновременном движении четырёх клавиш.

---

## 9. Поле аналога ещё нужно подтвердить аппаратно

Статически наиболее вероятное основное значение:

```text
A0 bytes 4..5, big-endian
```

Но необходимо проверить:

- W меняет именно W descriptor;
- значение плавно проходит полный ход;
- возвращается после отпускания;
- диапазон стабилен;
- нет необходимости вычитать baseline;
- нет инверсии;
- поля `6..7`, `16..19` не являются более подходящим нормализованным travel;
- primary value не является слишком шумным raw ADC.

Число в диапазоне `0…1600` ещё не доказывает готовый joystick analog.

---

## 10. Обязательные вопросы к параллельной реализации

Просьба ответить по пунктам:

### A. Машина состояний

Показать псевдокод и raw instructions для:

```text
A8 handler
A9 handler
A0 scheduler
```

с точными адресами flags.

### B. Почему `A0` живёт после `A9`

Указать конкретный persistent flag или ветку control flow. Если такого нет, признать, что финальный `A9` останавливает stream.

### C. Исходный аппаратный лог

Нужен полный лог с:

- TX/RX hex;
- timestamps;
- digital events;
- финальным `A9`;
- минимум пятью секундами наблюдения после него.

### D. Отрицательный тест

```text
A9
A8
A9 немедленно
слушать 5 секунд
```

Ожидание текущего анализа: устойчивого `A0` нет.

### E. Положительный контроль

```text
A9
A8
не отправлять A9 4 секунды
```

Ожидание: три стартовых sweep `A0`.

Затем отправить `A9` и проверить прекращение новых packets.

### F. Цифровой ввод во время активного `A8`

Одновременно наблюдать:

- boot keyboard interface;
- NKRO/digital interface;
- Windows low-level hook;
- vendor `A0` interface.

Нужно подтвердить normal digital input именно во время активного `A8`, а не только после `A9`.

## 11. Что может объяснить реальную работу подхода

Если новый аппаратный лог действительно показывает устойчивый `A0` после финального `A9`, возможны варианты:

1. Мы пропустили второй persistent telemetry flag.
2. Scheduler имеет другую ветку, которую неправильно декодировали.
3. Тестируется другая firmware revision.
4. В лог попала очередь старых packets.
5. Из-за framing отправляется не тот opcode, который предполагается.
6. Существует второй producer packets с marker `A0`.
7. Критическая WCH/QingKe XW инструкция декодирована неверно.

Для каждого варианта нужен конкретный адрес, raw bytes или аппаратное доказательство.

---

## 12. Когда stock-путь следует признать непригодным

Подход `A8/A0` непригоден для production HallJoy, если подтвердится хотя бы одно:

- `A9` прекращает `A0`;
- активный `A8` подавляет штатные буквы;
- частота четырёх WASD слишком низкая;
- нет надёжного полного snapshot;
- нет sequence number и невозможно обнаруживать потери;
- analog field слишком шумное или запаздывает;
- crash может оставить клавиатуру в service mode;
- восстановление требует переподключения.

Тогда практические варианты:

### Исследовательский workaround

Держать `A8`, получать `A0`, а цифровую клавиатуру синтезировать на host. Это сложно и не равно штатному hardware HID.

### Production-вариант

Модификация прошивки:

1. отделить `telemetry_enable` от `service_mode`;
2. оставить normal digital scan активным;
3. добавить плотный WASD/full-matrix report;
4. добавить sequence и firmware timestamp;
5. убрать one-key-per-packet bottleneck;
6. сделать безопасную enable/disable команду.

---

## Итоговый эксперимент, который разрешит спор

### Normal state

```text
send A9
drain input
wait 1 s
press W
confirm digital W and no A0
```

### A8 active

```text
release all keys
send A8
do not send A9
listen 4 s
slowly press/release W for 3 s
```

Логировать digital и `A0` одновременно.

### Stop

```text
send A9
drain input for 2 s
then press/release W for 3 s
```

Решающая проверка:

```text
есть ли новые W-correlated A0 после drain, выполненного уже после A9?
```

- Если **да**, текущий статический анализ неполон: нужно искать persistent producer.
- Если **нет**, `A9 → A8 → A9` не даёт постоянный аналог, и потребуется другой stock-механизм или модификация прошивки.

---

## Вывод

`A8 → A0` остаётся наиболее вероятным stock-путём настоящей Hall-телеметрии.

Но утверждение, что немедленная последовательность:

```text
A9 → A8 → A9
```

одновременно:

- восстанавливает штатные буквы;
- оставляет постоянный `A0`;
- даёт свежий полный набор 68 клавиш;

противоречит обнаруженной машине состояний.

Это не окончательное доказательство невозможности. Это проверяемая критика. Для её опровержения нужен точный альтернативный control flow либо аппаратный лог, исключающий очередь и показывающий новые W-correlated `A0` спустя несколько секунд после финального `A9`.
