# Архитектурный обзор HallJoy — 2026-09-06

## 2026-09-06 — Owner clarification: preserve automatic Sayo letter mapping

The owner requires automatic user-configured letters with no manual assignment,
setup wizard or mandatory confirmation, and reports no complaints about current
behavior. This supersedes earlier blanket prohibitions on Sayo letter learning:
physical depth remains measured independently; automatic letter association is
intentional. RM-03 now preserves it and tests ambiguous correlation (addedCount==1
already guards multiple new HID keys in one report; cross-report candidates need
review). No per-press activation-threshold delay was established. Treat stale-depth
fallback separately according to its intended digital/analog contract. Do not
remove Sayo, replace letters with physical-only controls, or label learning itself
P0. Reconcile old HJ-V14-P0-003 subclaims rather than copying its blanket verdict.
See FULL_AUDIT_EXECUTION_ROADMAP_2026-09-06.md v1.1, section 0, for other potential
intent traps: fallback/shadow removal, single-instance, async save, process
isolation and release scope. Proposed rewrites require Purpose/compatibility
review and evidence; product behavior changes require an explicit product decision.
Only documentation changed in this clarification; no new runtime PASS is claimed.


## Вывод и границы

Нужна последовательная переработка нескольких границ, а не переписывание всей
программы. Главные кандидаты: freshness вывода, неизменяемая конфигурация,
завершение миграции Provider V2, единый владелец сохранения и восстановления.

Это анализ текущих исходников, а не результат нового runtime/нагрузочного прогона.
Сценарии риска ниже установлены по коду; их частота и стоимость на конкретном
железе не измерялись. Числа ускорения не заявляются. Наличие сложного кода,
комментария future или незакрытого старого документа само по себе не доказательство
дефекта. Исторические исправления не объявляются сломанными повторно.

Прочитаны ENGINEERING_WORKING_METHOD, текущий handoff, release-readiness audit,
mega-roadmap и релевантные исходники. Производственный код, EXE и пользовательские
настройки не изменялись. Тесты с клавиатурой/виртуальным геймпадом не запускались.

## AR-01. Output health не замыкает freshness всего пути — высокий приоритет

Основание: vigem_output_process_host.cpp:330–410. При WAIT_TIMEOUT дочерний
процесс публикует собственный heartbeat; при отсутствии обновления продолжает
цикл. Отдельного дедлайна прогресса родительского расчёта в этом цикле нет.
SnapshotPayloadV1 содержит timestampUs, но просмотренная ветка применения
не использует его как срок годности. OutputRuntime проверяет свежесть heartbeat
дочернего процесса (vigem_output_runtime.cpp:410). Realtime watchdog в
app.cpp:1348 проверяет завершение потока, а не продвижение вычисления.

Сценарий: последнее состояние ненулевое, realtime завис внутри живого родителя,
дочерний процесс продолжает отвечать. Его heartbeat не доказывает свежесть
последнего управляющего состояния. Изоляция процессов сама по себе не закрывает
этот случай. Это архитектурный риск, а не утверждение о воспроизведённом сейчас
«залипании».

Предпочтительно: отдельная ограниченная по времени аренда работоспособности
producer, обновляемая только после успешного продвижения расчёта, и независимое
обнуление в output child. Потеря аренды должна быть видна supervisor.
Нельзя просто обнулять по времени последнего ИЗМЕНЕНИЯ отчёта: дедупликация
намеренно не отправляет одинаковые отчёты, а долгое удержание клавиши корректно.
Heartbeat producer должен быть связан с прогрессом, а не отдельным таймером,
который продолжает жить при зависшем расчёте.

Проверка: fake transport + управляемые часы; живой, но остановившийся producer,
долгое неизменное удержание при живом producer, зависший UI, потеря wake,
запоздалый пакет старой generation. Измерить deadline обнуления и ложные сбросы.

## AR-02. Настройки ещё не стали одной неизменяемой конфигурацией — высокий приоритет

Основание: profile_runtime_gate.h; global_profiles.cpp; settings.cpp;
key_settings.cpp:93,202; backend_curve.cpp:111,132.
Вчерашний CommitLease закрывает целостность загрузки профиля относительно
Backend_Tick. Но обычные setters и действия редактора всё ещё работают с
глобальными полями и отдельными публикациями; не все они проходят этот gate.

FastSnapshotLoad содержит for (;;) с повтором при незавершённой записи.
Для кодов >=256 чтение использует shared_mutex. Поэтому единый контракт
«realtime никогда не ждёт писателя» пока отсутствует. При вытеснении writer
неограниченный retry может увеличивать хвост задержки. Это не доказательство
обычного длительного зависания на каждом изменении.

Предпочтительно: подготовленная RuntimeConfig с номером generation, содержащая
настройки, bindings и описания кривых. UI строит следующую версию, тик получает
одну pinned-версию, публикуемую целиком. Реализация lifetime должна исключать
удаление больших объектов и последнее освобождение памяти на realtime-потоке.
Один atomic shared_ptr без анализа reclamation не является готовым решением.

Проверка: изменения обычных контролов и профилей при конкурентных тиках,
вытесненный writer, полная область кодов, смешанные значения внутри одного XUSB,
p99/max тика, allocations и ожидания на realtime.

## AR-03. Расширенные коды поддержаны функционально, но неравноправны по стоимости

Основание: key_settings.cpp:20,45,202–235; backend_curve.cpp:132–171.
Для HID <256 есть атомарный снимок и cache.curves; для >=256 — unordered_map
под shared_mutex, а кеширование кривой в этом месте ограничено hid <256.
GetUseUnique и Get выполняют отдельные чтения. Полный домен bindings уже шире.

Это конкретная незавершённость расширения модели: поддержка Fn/расширенных
назначений не означает одинакового пути выполнения. Она особенно важна, если
такие коды используются в активно вычисляемом управлении.

Объединить с AR-02: индексируемая подготовленная таблица всего поддержанного
домена или компактная таблица только используемых keys, с одной generation.
Не расширять все структуры без оценки памяти: таблица ключей и тяжёлый кеш
кривых имеют разную цену.

Проверка: одинаковая конфигурация обычных и расширенных кодов, счётчики
блокировок/промахов и стоимость тика; проверить все 1033 допустимых кода.

## AR-04. Миграция Provider V2 сохраняет двойную работу и несколько истин

Основание: backend.cpp:3079–3135,1643–1733,2146–2159.
Тик сначала получает dense snapshot, затем lease V2 и сверяет публикации.
При подходящем V2 он авторитетен; при недоступности остаётся legacy route.
BuildConfiguredReportPair строит qualified и shadow отчёты; второй BuildReport
в просмотренной функции вызывается даже при неeligible shadow.

Это реальная повторная работа, но её доля в CPU пока не измерена.
Само сравнение полезно для квалификации. Ошибка была бы убрать его и fallback
до доказательства полноты V2 и назвать это оптимизацией.

Предпочтительно: закончить квалификацию V2, закрепить явные состояния
V2-supported / legacy-only / invalid-or-stale, затем вынести постоянное
сравнение в qualification-сборку или ограниченный диагностический режим.
Не путать отсутствие V2 у совместимого провайдера с повреждением современного
снимка. Старый compatibility reader должен иметь конкретных пользователей,
владельца и критерий удаления.

Проверка: полное совпадение output, ранний analogue travel, topology/capacity,
расширенные ключи, unplug/reconnect, поколение между двумя captures; A/B CPU
и p99/max. Legacy-shadow нельзя убирать только ради зелёной сборки.

## AR-05. UI владеет дорогим сохранением и частью восстановления

Основание: keyboard_bind_panel.cpp:135–145; keyboard_ui.cpp:205;
settings_ini.cpp:637–714; ini_util.cpp:215–239,350; app.cpp:1348–1381.
Действие назначения вызывает полное сохранение bundle синхронно.
Общий атомарный writer сериализует настройки и bindings, сбрасывает данные
и заменяет файл. Это правильно для целостности, но потенциально дорого для UI.
В той же UI-обработке таймера расположены проверки восстановления realtime,
output и overlay. Медленный диск/занятый UI задерживает эти проверки.

Предпочтительно: единый persistence service с очередью неизменяемых снимков,
объединением ещё не начатых сохранений и подтверждённой saved-generation.
«Применено в памяти», «ожидает записи» и «сохранено» должны различаться.
Перед сменой профиля и выходом нужен явный барьер и обработка ошибки:
асинхронность без этого создаст потерю последних изменений.
Health/recovery переносить к владельцу runtime, независимому от UI.

Проверка: медленный/заблокированный файл, отказ replace, серия изменений,
смена профиля при незавершённом save, закрытие окна, повторная попытка.
Измерить длительность обработчиков UI и возраст последней сохранённой версии.

## AR-06. Разделение ответственности остановилось на середине

Основание: backend.cpp совмещает arbitration, compatibility, конфигурацию XUSB,
shadow qualification, часть lifecycle и диагностику; analog_host_client.cpp —
IPC, процессы, сбор снимков, совместимые API и восстановление.
keyboard_subpages.cpp содержит порядка 415 КБ исходного текста.
Размер — индикатор для просмотра, а не самостоятельное основание переписывать.

Хорошие выделенные границы уже есть: configured_xusb builder, snapshot broker,
process generation supervisor, output transport. Их стоит сохранить и довести
до конца. Особенно полезен независимый от Win32/UI расчёт:
InputSnapshot + RuntimeConfig + previous controller state -> ControllerFrame.
Побочные эффекты оставить adapters и владельцам runtime.

Выделение файлов без изменения ownership не устраняет риск отвалов.
Переносить сначала один законченный контракт, сохранять characterization
поведения и удалять прежнюю ветку после переключения.
Проверка: deterministic replay одних входных снимков, идентичный XUSB,
порядок shutdown/recovery, отсутствие новых allocations на тик.

## AR-07. Граница экспериментального функционала не задаётся единым правилом

Основание: native_analog_backends.def:7–23 и HallJoy.vcxproj.
Hero84 обычный descriptor включён в основной каталог; ND75 требует отдельного
experimental define; DrunkDeer/MCHOSE здесь привязаны к diagnostic define.
Это не доказательство небезопасности Hero84, но релизная граница задаётся
разными локальными условиями и может расходиться со списком поддержки.
Тот же вопрос уже открыт в release-readiness R-02.

Предпочтительно: один manifest capability/release tier, из которого проверяются
или генерируются каталог сборки и таблица поддержки. «Есть код»,
«есть protocol proof», «прошла физическая квалификация» и «входит в stable»
должны быть разными состояниями. Не подменять protocol admission маркетинговым
списком: проверка конкретного устройства остаётся обязательной.

Проверка: обычный бинарник содержит только разрешённые claimants;
каждая diagnostic-сборка имеет ожидаемый каталог; support matrix совпадает.
Решение о включении семейства требует собственной evidence.

## AR-08. Завершённость изменений плохо выражена в проверках и документации

Основание: persistence_transaction_static_audit.py использует проверки наличия
текстовых фрагментов; аналогичный ложный красный descriptor-regex уже описан
в RELEASE_READINESS_AUDIT_2026-09-05.md.
Это полезные wiring guards, но они чувствительны к безвредному рефакторингу и
не заменяют проверку фактических interleavings. В проекте также есть настоящие
поведенческие тесты — называть весь набор «проверкой строк» неверно.

Handoff одновременно содержит свежий hash 44CFC... и ниже старые «active/newest»
описания других artifacts. Термины future/F2 остаются в заголовках уже работающего
output IPC. Старый release-readiness документ содержит qualification прежнего
EXE. Это создаёт риск принять завершённость одного поколения за другого.

Предпочтительно: короткая текущая матрица «компонент -> route -> artifact ->
проверено -> pending -> removal gate», история отдельно. Для каждого перехода
V2/config/lifecycle — явное условие удаления compatibility слоя.
Архитектурные инварианты проверять production-linked state-machine/fault tests;
текстовые guards оставить для простых условий сборки.

Проверка: отчёт о квалификации не может прикрепляться к другому hash;
поведенческий oracle падает на старой реализации и не зависит от пробелов
в объявлении C++. Внешний exit 1 последней сборки остаётся отдельной незакрытой
аномалией tooling; в этом обзоре его причина не установлена.

## Сравнение направлений переработки

Это предложения для следующего решения, а не уже принятые production changes.

| Граница | Локально | Поэтапно (предпочтительно) | Полная замена |
|---|---|---|---|
| Freshness | добавить наблюдение progress | producer lease + child neutral + recovery state | новый output IPC; пока не обоснован |
| Config | ограничить retry и унифицировать чтение | immutable RuntimeConfig с управляемым lifetime | заменить все editors/settings сразу; большой риск миграции |
| Provider | выключать лишний shadow только в доказанных режимах | квалифицировать V2, затем удалить лишние пути | заменить host/provider ABI заново; теряет уже проверенные границы |
| Persistence | объединять частые UI saves | отдельный writer с generation и barriers | новая БД; нет доказанной необходимости |
| Lifecycle/UI | вынести отдельные проверки | единый runtime owner, UI отправляет команды | переписать приложение/framework; выгода пока не доказана |

Каждый implementation package требует решения по ENGINEERING_WORKING_METHOD
и проверки поведения до/после. Без измерений нельзя обещать «лучше во всём»:
меньше CPU может стоить памяти; асинхронный writer усложняет shutdown;
жёсткий freshness deadline при плохом выборе создаёт ложные обнуления.

## Рекомендуемый порядок

1. AR-01: закончить контракт свежести вывода; fake-only тесты до hardware.
2. AR-02 + AR-03: одна конфигурация тика, включая обычный редактор и extended keys.
3. AR-04: завершить V2 qualification и убрать двойной путь по removal gate.
4. AR-05: persistence и runtime supervision независимо от UI.
5. AR-06: выделять модули по этим контрактам, не делать косметическую перекладку.
6. AR-07 + AR-08: вести параллельно; обязательны до stable release.

Не переписывать без новых оснований: versioned IPC slots, generation ownership,
существующую процессную изоляцию UAP/ViGEm, общий XUSB builder и атомарный replace
профиля. Это полезные части текущего фундамента.
