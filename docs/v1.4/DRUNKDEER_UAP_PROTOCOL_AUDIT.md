# Аудит поддержки DrunkDeer в UAP/Soup

Уточнение 2026-09-09: четыре ранее предположенные позиции G65 навигации
заменены в исходнике native diagnostic-карты на позиции официального Antler
по решению владельца: 35/56/77/98. Старые физические логи эти четыре клавиши
не проверяли; измеренные позиции сохранены. Актуальный разбор и границы
внедрения: `../current/DRUNKDEER_LAYOUT_IDENTIFICATION.md`. Текст ниже исторический.

Дата аудита: 20 августа 2026 года.

Статус: аудит исходного кода и первый пригодный физический лог завершены.
Turbo mode действительно отключал аналоговую выдачу, но после его выключения
лог независимо подтвердил неверную общую UAP-таблицу G65 как минимум для Esc,
Right Shift, Right Alt, Down, Right и Up. Повторный разбор дал 45 прямых
raw-offset/HID пар. Для PID `2382` теперь собрана отдельная статическая ANSI G65-
таблица; полный повтор всей клавиатуры отменён. Остался короткий физический тест
частоты и правильных имён. Этот документ описывает Windows x64 путь сборки.

## Краткий вывод

HallJoy не переставляет стрелки после получения данных от UAP. Turbo объяснял
полное отсутствие аналоговой выдачи, но не перестановку после его выключения:
физический Right доказан в `(5,14)`, где общая UAP-таблица публикует Left;
Down доказан в пустой для UAP `(5,13)`, Up — в `(4,13)`, размеченной как
Right Shift. Кроме стрелок доказаны неверные Esc `(1,0)`, Right Shift `(4,12)`
и Right Alt `(5,9)`. Это уже физическое, а не только статическое доказательство.

Главная архитектурная проблема UAP: все устройства с VID `352D` — G60, G65, A75,
G75 и неизвестные модели — опрашиваются одной командой и декодируются одной
непроверенной таблицей `6x21`. PID используется только для отображаемого названия,
но не для выбора раскладки.

Текущая UAP-таблица считает:

- `(5,12)` — `Menu/OEM_1`;
- `(5,13)` — пустая ячейка;
- `(5,14)` — `Left`;
- `(5,15)` — `Down`;
- `(5,16)` — `Right`.

На G65 физический блок стрелок занимает `(5,12)..(5,14)`: физический `Right`
действительно попадал в общую ячейку Left. Отдельная модельная таблица исправляет
этот сдвиг до публикации в HallJoy.

## Статическая таблица G65 ANSI

Новая `G65AnsiMap()` выбирается только для PID `352D:2382`. Она содержит все 68
физических позиций: 66 уникальных стандартных USB HID usages и два независимых
расширенных кода Soup/UAP, `Fn=0x409` и `Menu/Fn2=0x403`. Цифровые события не
участвуют в runtime-публикации, выборе ячейки или обучении.

| Участок | Raw matrix | Статическая интерпретация |
|---|---|---|
| верхний ряд | `(1,0)..(1,13)`, `(1,15)` | `Esc`, `1..0`, `-`, `=`, `Backspace`, `Delete` |
| Q-ряд | `(2,0)..(2,13)`, `(2,15)` | `Tab`, `Q..P`, скобки, `Backslash`, `End` |
| A-ряд | `(3,0)..(3,11)`, `(3,13)`, `(3,15)` | `Caps`, `A..L`, `;`, quote, `Enter`, `PgUp` |
| Z-ряд | `(4,0)`, `(4,2)..(4,13)`, `(4,15)` | оба `Shift`, `Z..Slash`, `Up`, `PgDn` |
| нижний ряд | `(5,0..2)`, `(5,6)`, `(5,9)`, `(5,12..14)` | `Ctrl`, `Win`, `Alt`, `Space`, right `Alt`, `Left/Down/Right` |
| служебные слои | `(5,10)`, `(5,11)` | независимый аналог `Fn=0x409`, `Menu/Fn2=0x403` |

45 из этих стандартных позиций непосредственно измерены логом firmware `0012`.
Остальные позиции завершают те же подтверждённые ряды согласно официальной ANSI
65% геометрии G65 и её правому столбцу `Delete/End/PgUp/PgDn`.

## Проверенная цепочка данных

```text
DrunkDeer HID interface
  -> Soup hwHid (OVERLAPPED ReadFile/WriteFile)
  -> AnalogueKeyboard::getActiveKeysDrunkdeer()
  -> общая таблица 6x21, raw / 40
  -> UAP Device::update_from_keyboard(), HID-таблица 0..255
  -> изолированный HallJoy analog-host process
  -> shared-memory dense snapshot
  -> HallJoy backend / overlay / ViGEm
```

HallJoy загружает ABI1-плагин только в дочернем crash-isolated процессе. Дочерний
процесс получает приватный плотный снимок из 256 HID-кодов, проверяет конечность
чисел, ограничивает значения диапазоном `0..1` и передаёт снимок родителю через
shared memory. На этом участке нет перестановки `Left` и `Right`: одинаковые HID-
коды только объединяются между устройствами по максимальному значению.

Проверялся именно источник сборки:

- Soup закреплён на commit `b02796b0b20276277c8a4b4d3759643eeab43ff7`;
- `tools/dependency-lock.json` закрепляет хеши overlay-файлов;
- `build_fixed_plugin.ps1` копирует overlay в Soup перед компиляцией и проверяет
  его хеш;
- фактический DrunkDeer-код находится в
  `third_party/UniversalAnalogPluginFixed/overlay/Soup/soup/AnalogueKeyboard.cpp`.

## Как UAP распознаёт DrunkDeer

Soup перебирает все HID-интерфейсы Windows и открывает их с
`GENERIC_READ | GENERIC_WRITE`, shared read/write и `FILE_FLAG_OVERLAPPED`.
Интерфейс считается DrunkDeer-аналогом, если:

1. VID равен `352D`;
2. в input report descriptor существует report ID `04`.

Проверка `hasReportId(4)` относится только к входному report. Она не доказывает,
что выбранный интерфейс поддерживает выходную команду `B6 03 01`, имеет нужные
размеры report или вообще является интерфейсом матрицы глубины.

Известные PID:

| PID | Название Soup | Состояние в исходнике |
|---:|---|---|
| `2382` | DrunkDeer G65 | `untested` |
| `2383` | DrunkDeer A75 | один PID для ANSI/ISO; возможно также A75 Pro |
| `2384` | DrunkDeer G60 | `untested` |
| `2386` | DrunkDeer G75 ANSI | `untested` |
| `2391` | DrunkDeer G75 JP | `untested` |

Неизвестный PID с VID `352D` и report ID `04` тоже принимается, если устройство
возвращает непустое product name. После обнаружения PID больше не участвует в
декодировании.

Если диагностический лог покажет PID `2384` на клавиатуре, проданной как G65,
это отдельно подтвердит ошибку идентификации прошивки или веб-драйвера. Но для
текущего UAP это не меняет раскладку: G60 и G65 всё равно получают одну таблицу.

## Транзакция на проводе

Каждый цикл UAP выполняет следующее:

1. создаёт/открывает глобальный Windows mutex `DrunkDeerMtx` и ждёт его бесконечно;
2. пытается отбросить накопленные входные reports;
3. отправляет 64 байта: `04 B6 03 01`, затем нули;
4. последовательно и без таймаута читает три input report;
5. отбрасывает первые пять байт каждого ответа;
6. склеивает оставшиеся байты строго в порядке прихода;
7. читает индекс `row * 21 + column` и делит байт на `40.0`;
8. вручную освобождает mutex.

При обычных reports `3 x 64` получается `177` payload-байт. Таблица использует
только индексы `0..121`; остальные 55 байт (из них 51 после 126 ячеек матрицы)
игнорируются. Семантика этих байтов и пятибайтовых заголовков UAP не проверяется.

## Подтверждённые дефекты исходного кода

Ниже «подтверждён» означает, что дефект виден непосредственно в выполняемом
исходном коде. Это не означает, что каждый дефект уже проявился у владельца G65.

| ID | Важность | Дефект | Последствие |
|---|---|---|---|
| DD-UAP-01 | критическая для корректности | Одна таблица `6x21` применяется ко всем VID `352D`; PID влияет только на название. | Невозможно корректно поддержать модели с различающимися координатами без изменения кода. Вероятный корень перестановки стрелок G65. |
| DD-UAP-02 | высокая | Выбор интерфейса проверяет лишь VID и наличие input report ID `04`; usage page, usage, input/output lengths и протокольный handshake не проверяются. | Может быть открыт не тот интерфейс составного HID или несовместимая прошивка. |
| DD-UAP-03 | критическая | Три ответа не проверяются по report ID, команде, статусу, номеру/offset пакета, checksum или порядку. | Чужой streaming report, изменение порядка или ошибка firmware бесшумно превращаются в другую раскладку/глубину. |
| DD-UAP-04 | критическая, memory safety | Проверяется только `empty()`. При размере `1..4` выражение `size()-5` переполняется, `data()+5` выходит за объект. При суммарном payload меньше 122 байт последующее индексирование тоже выходит за границы. | Огромная ошибочная аллокация, out-of-bounds read, исключение или падение UAP-процесса. |
| DD-UAP-05 | высокая | Результат `sendReport()` игнорируется. | После неудачной записи код всё равно ждёт три ответа и не сообщает истинную причину. |
| DD-UAP-06 | критическая для стабильности | Generic `WriteFile` и каждый `ReadFile` завершаются через `GetOverlappedResult(..., TRUE)` без таймаута. | Один потерянный пакет способен навсегда повесить worker. В том же overlay уже есть bounded/cancel-and-drain transport для Madlions, но DrunkDeer его не использует. |
| DD-UAP-07 | высокая | `DrunkDeerMtx` ждётся с `INFINITE`; результат ожидания не проверяется; lock/unlock не RAII. | Shutdown не может прервать ожидание. Исключение между lock и unlock оставляет mutex abandoned. Все DrunkDeer-устройства и другие процессы с тем же именем сериализуются. |
| DD-UAP-08 | средняя | `discardStaleReports()` без ограничения повторяет чтения, пока очередное чтение не станет pending; report ID не фильтруется. | При непрерывном потоке возможен долгий CPU-spin; длительность очистки не ограничена. |
| DD-UAP-09 | высокая для диагностики | Любой сырой байт делится на фиксированные `40`, затем UAP/HallJoy ограничивает результат до `1.0`. | Значения `41..255`, иной scale или повреждённые данные выглядят как нормальное полное нажатие; исходное доказательство теряется. |
| DD-UAP-10 | высокая для отдельных ячеек | `Fn` преобразуется в `0x409`, `Menu/OEM_1` в `0x403`, но плотный снимок имеет только 256 элементов и отбрасывает коды `>=256`. | Эти две размеченные ячейки DrunkDeer всегда исчезают из HallJoy. Это также объясняет «нет аналога», если физический `Left` G65 находится в общей ячейке `(5,12)`. |
| DD-UAP-11 | высокая | `clear_snapshot()` находится только в нормальной ветке worker. При исключении catch отмечает fault, но не обнуляет последний снимок. | После malformed report может кратковременно остаться замороженное ненулевое нажатие до удаления устройства/перезапуска host. |
| DD-UAP-12 | средняя | Любой один пустой из трёх reports немедленно помечает устройство disconnected; локального retry и различения transient error нет. | Краткий сбой превращается в закрытие и повторное обнаружение устройства. |
| DD-UAP-13 | средняя, производительность | Цель — цикл 1000 мкс, но каждый цикл создаёт kernel mutex handle и event, делает write + 3 reads, несколько heap-копий Buffer, новый vector и сканирует всю таблицу. | Лишние системные вызовы, аллокации и jitter; реальная частота ограничена четырьмя HID transfers. |
| DD-UAP-14 | средняя | Telemetry жёстко сообщает `6x21`, 126 slots и 41 level для любой DrunkDeer. | Telemetry повторяет предположение декодера и не может доказать реальную геометрию или scale модели. |
| DD-UAP-15 | высокая | Неизвестные PID допускаются к общей таблице, а G65/G60/G75, помеченные `untested`, считаются production-compatible. | Новая или иначе прошитая модель может давать правдоподобные, но неверно подписанные значения. |

Дополнительная неэффективность DD-UAP-13 по одному успешному циклу:

- создание и закрытие named mutex handle;
- создание и закрытие event для write;
- одна 64-байтовая команда;
- три блокирующих чтения и три копии общего read buffer;
- отдельная аллокация объединённого payload;
- динамический рост списка до 82 активных клавиш;
- обнуление 256-float dense table и повторный проход по ней в host.

## Что является риском, но пока не доказанным дефектом устройства

- Не доказано, что пять header bytes действительно постоянны или содержат
  sequence/offset. Диагностика логирует первый набор и счётчик изменений.
- Не доказано, что `40` — правильный максимум для каждой модели и firmware.
- Не каждая позиция полной статической G65-таблицы была непосредственно поймана
  редким v2-опросом: 45 из 68 физических позиций измерены, остальные, включая
  raw-ячейки `Fn` и `Menu/Fn2`, завершены по доказанной структуре рядов,
  существующей Soup/UAP-таблице и официальной геометрии. Поэтому короткая
  физическая проверка ещё нужна, но повторять полный сбор матрицы не требуется.
- Не доказано, что веб-драйвер реально видит PID G60: это подтвердит строка
  `[drunkdeer.enumeration]` с аппаратным PID.
- Не доказана неисправность клавиатуры. Она будет вероятна, если разные физические
  стрелки дают одну сырую ячейку либо `Left` не меняет ни одной ячейки при исправном
  цифровом HID-событии.

## Что должен решить полученный лог

Диагностическая сборка читает тот же read-only запрос `04 B6 03 01`, но не использует
цифровую точку активации в аналоговом runtime. Цифровые события и raw-кадры
записываются независимо. Только после закрытия EXE отдельный анализатор смотрит
назад от digital edge к уже начавшемуся аналоговому эпизоду; production получает
лишь заранее проверенную статическую таблицу модели.

Нужные доказательства:

1. `[drunkdeer.enumeration]` — реальный PID, usage, input/output sizes и выбранный
   HID interface;
2. `[drunkdeer.report_headers.initial]` и rollup — содержимое и стабильность
   заголовков трёх пакетов;
3. `[drunkdeer.raw_cell.press/release]` — физическая координата и диапазон raw для
   каждого отдельного нажатия;
4. `[drunkdeer.digital.press/release]` — какая физическая стрелка нажималась,
   независимо от глубины и без влияния на аналоговую таблицу;
5. session summary — ошибки транспорта и устойчивость частоты.

Ожидаемая развилка:

| Результат лога | Вывод |
|---|---|
| `Right` меняет `(5,14)`, а `Left` — `(5,12)` или `(5,13)` | Подтверждена неверная общая таблица UAP для этой G65/firmware. |
| `Right=(5,16)`, `Left=(5,14)`, но HallJoy показывает другое | Искать ошибку после декодера; по текущему аудиту это маловероятно. |
| `Left` имеет цифровое событие, но не меняет ни одной raw-ячейки | Вероятна проблема firmware/режима/самой клавиатуры либо другой запрос для этой модели. |
| Два физических направления меняют одну raw-ячейку | Вероятна ошибка firmware/матрицы клавиатуры. |
| PID равен `2384`, хотя устройство G65 | Подтверждена ошибочная идентичность G60; раскладка UAP всё равно остаётся общей. |
| Headers/порядок пакетов меняются | Текущая склейка UAP по порядку прихода непригодна; нужен разбор header. |

## Решение до получения лога

Не вносить сейчас модельный сдвиг или таблицу наугад. Подтверждённые transport и
memory-safety дефекты UAP существуют независимо от результата теста, но исправление
только стрелок до получения raw-координат было бы новым костылём.

После лога предпочтительный production-путь — собственный DrunkDeer backend, а не
расширение текущей ветки Soup. В проекте уже есть диагностический фундамент, но он
пока намеренно не считается финальной поддержкой.

Минимальные требования к production-реализации:

1. строгий выбор интерфейса по VID/PID, usage, report sizes и успешному read-only
   capability proof до объявления ownership;
2. отдельный проверенный layout descriptor для каждой модели/варианта firmware,
   с безопасным fallback «не поддерживается»;
3. проверка каждого пакета: длина, report ID, command/status, chunk/offset/sequence,
   допустимый raw range;
4. одна bounded транзакция с cancel-and-drain для write и всех трёх reads;
5. persistent handles/events/buffers без аллокаций и открытия mutex на каждом poll;
6. RAII mutex с таймаутом и возможностью остановки;
7. публикация только целого когерентного кадра; при ошибке — neutral snapshot,
   ограниченный retry и контролируемый reopen;
8. сохранение raw telemetry до нормализации, без скрывающего ошибки clamp;
9. явная поддержка HID-кодов за пределами 255 либо осознанное исключение Fn/OEM;
10. hotplug ownership до открытия интерфейса UAP, чтобы один HID не читали два
    backend одновременно;
11. protocol tests, malformed/short/reordered report tests и hardware fixture для
    каждой заявленной модели.

  extended-code loss, worker pacing и shutdown;
- `src/HallJoyProject/HallJoy/analog_host_client.cpp`: валидация и перенос dense

## Результат первого физического запуска и diagnostic schema 2

Полученный 20 августа 2026 года `HallJoyStabilityTrace (2).log` не доказал
отсутствие аналога у G65. Он отклонён как результат дефектной diagnostic
schema 1: 40-байтовые x64 keyboard RAWINPUT-пакеты отбрасывались, payload не
проверялся по `B7`/chunk ID, а mmap-preallocation оставила 1-МиБ файл с NUL-хвостом без
надёжного финализатора. SHA-256 отклонённого лога:
`CAF36C82D966C3FD9021CDFB451924060CAF49DEC527B2F27631527AB3410B2A`.

Первая реализация schema 2 исправила формат доказательств, но ввела ошибочную
гипотезу о cadence:

- после `HidD_FlushQueue` она посылала start ровно один раз и ожидала
  непрерывный tracking stream;
- принимает только envelope `04 B7`, собирает chunk ID `0/1/2`, допускает
  restart кадра новым chunk 0, отвергает duplicate/out-of-order и сохраняет
  все 177 payload-байт, включая 51 байт за матрицей;
- использует первые `59+59+8` байт как 126 ячеек того же UAP `6x21`, поэтому
  corrected build выбирает отдельную статическую G65-таблицу строго по PID 2382;
- принимает корректный 40-байтовый `RAWKEYBOARD`; каждый digital edge
  синхронно фиксирует полный текущий аналоговый payload и его возраст;
- пишет schema-2 лог прямым append без preallocation, синхронно flush-ит
  критические строки и оставляет пригодный префикс даже после hard kill.

Команда и framing дополнительно сверены с официальным текущим Antler:
Keystroke tracking отправляет `B6 03 01`, принимает `B7` chunks `0/1/2` с
раскладкой `59+59+8` key-height bytes и отправляет `B6 03 00` при остановке.
Проверенный официальный JS: SHA-256
`47371FE3FB5B2CDC2C54F86CB5AD71E4937ACEB8DCCA93BF79B53CA42D345745`.

Физический `HallJoyStabilityTrace (3).log`, SHA-256
`5F62728C403572D76112C3FAFAC42D846AEB3CE56EFF79285A01AC40E721FFD2`,
доказал one-shot semantics firmware `0012`: 71 runtime-сеанс дали по одному
успешному кадру и затем по три timeout `258`. За 74 секунды было 72 proof и 71
runtime frame, поэтому «start один раз» непригоден для realtime. Одновременно
лог доказал целостность schema 2: 643 197 байт, 2693 строки, ноль NUL,
полный `session.end`, 66 digital press и 68 release.

При выключенном Turbo физические координаты стрелок из этого редкого опроса:

| Digital HID | Физическая клавиша | Доказанный raw offset | Текущая UAP-интерпретация |
|---:|---|---|---|
| `0029` | Esc | offset `21`, `(1,0)`, raw до `40` | Backquote (`0035`) |
| `00E5` | Right Shift | offset `96`, `(4,12)`, raw `40` | пусто |
| `00E6` | Right Alt | offset `114`, `(5,9)`, raw `40` | пусто |
| `0051` | Down | offset `118`, `(5,13)`, raw `40/32` | пусто |

Таким образом Turbo объяснял отсутствие analog output, но независимо от него
общая UAP-таблица для G65 действительно неверна как минимум для шести клавиш.
Особенно прямо подтверждён исходный симптом: физический Right находится в ячейке,
которую общая таблица публикует как Left. Исправленный прямой офлайн-разбор
редкого v2 лога дал 45 устойчивых HID-сопоставлений и 17 HID-клавиш без попавшего
в удержание кадра. Предыдущие числа `20/32/9` были дефектом чрезмерно широкого
episode-overlap анализатора, а не ограничением самого лога.

Исправленная diagnostic-сборка повторяет доказанную UAP-транзакцию на одном
открытом HID:
`FlushQueue -> B6 03 01 -> B7[0] -> B7[1] -> B7[2]` для каждого кадра; named
mutex удерживается на всю write+read транзакцию, stop посылается один раз при
закрытии. Краткий сбой повторяет транзакцию на том же handle; reopen разрешён
только для подтверждённого disconnect или после 12 последовательных transient-
сбоев. Ненулевое состояние старше 350 мс обнуляется без закрытия устройства.
EXE: 2 361 856 байт, SHA-256
`AF602E45CFA14AB9905CBA76223D2F8D09C355DF56707E7A38C4D7DC1F8462D8`.
Portable/static gates, MSVC Release x64, normal WM_CLOSE, рост лога выше 2 МиБ
без NUL и сохранность direct-append лога после hard kill прошли. Runtime-код
цифрово-аналогового коррелятора удалён полностью; отдельный офлайн-анализатор и
регрессия глубокой digital actuation point прошли. Статический тест закрепляет
45 измеренных пар, все 68 уникальных физических кодов, расширенный 16-битный путь
`Fn/Menu`, PID-выбор и сжатый стрелочный блок. Лог отдельно фиксирует retry,
same-handle recovery, stale neutralization и требование reopen. Ожидается только
короткая проверка реальной частоты и поведения; повтор полного прохода не
требуется.

В этой сборке исторический `DrunkDeer A75 Pro` остаётся preset 0 и выбирается
по умолчанию. `DrunkDeer G65 ANSI` и `WASD Only` являются дополнительными
вариантами. `WASD Only` содержит только W/A/S/D в визуальной раскладке и никак
не сужает полный нативный аналоговый snapshot backend.

## Физическое подтверждение полной карты

Финальный пользовательский лог `HallJoyStabilityTrace (4).log`, SHA-256
`9BA60C932A71C9D488D9F8113779324E302FF6935B8979423265C3447CD7C21A`,
подтвердил PID `2382`, firmware `0012`, `mapped=68` и
`map=g65_full_static_v2`. За сессию получен 19 051 успешный кадр при 0 ошибках,
0 retry/reopen/stale-neutralization, 0 ignored/out-of-order/restart reports и
неизменных заголовках. Стабильная физическая частота составила в среднем
249,4 Гц (окна 244,4–250,0 Гц; худший интервал 6 001 мкс).

Главный ранее отсутствовавший факт теперь измерен напрямую: `Fn` в `(5,10)`
публикуется как `0x409` и достигает raw `40`, а `Menu/Fn2` в `(5,11)`
публикуется как `0x403` и также достигает raw `40`. Все четыре стрелки изменяют
свои отдельные правильные ячейки и достигают raw `40`. Пользователь подтвердил
правильное поведение. В логе были активны 47 из 68 mapped-позиций;
`Delete/End/PgUp/PgDn` в этом сеансе не нажимались.

Закрытие выявило независимый ViGEm output-worker timeout: после правильного
останова DrunkDeer worker ViGEm thread не присоединился за 3 секунды, поэтому
общий shutdown намеренно помечен poisoned и `session.end` содержит exit code 2.
Это открытый общий output-lifecycle дефект, а не опровержение DrunkDeer-карты
или её транспорта.
