## Дефекты

P1 — исправить в первую очередь; P2 — существенная ошибка, обычно требующая
определённого состояния файлов или действия пользователя.

### F-01 / P1 — Count раскладки не ограничивает ни память, ни работу загрузчика

Место: `src/HallJoyProject/HallJoy/keyboard_layout.cpp:540`, особенно 545–553;
автоматическая загрузка каталога — 860–902.

Из `[LayoutPreset] Count` проверяется только положительность. Значение сразу
передаётся двум `vector::reserve`, затем задаёт число чтений INI. Короткий
файл с `Count=2147483647` заставляет запрашивать огромные объёмы памяти;
меньшее значение способно надолго занять загрузку даже без записей K0..Kn.
Все `.ini` в Layouts автоматически читаются при инициализации: испорченная
или полученная от другого пользователя раскладка может мешать каждому запуску.

Доказательство: статический путь от файла до allocation/loop. OOM специально
не запускался. Предлагается ограничить размер входного файла, число ключей и
общий объём разбора до reserve; ошибочный preset пропускать с сообщением.
Граница должна соответствовать поддерживаемому редактором формату.

### F-02 / P1 — Переключение профиля фиксирует успех до загрузки файлов

Место: `keyboard_subpages.cpp:5929–5953`; `profile_ini.cpp:292–299`;
`settings_ini.cpp:322–327`; `global_profiles.cpp:190` и далее (список профилей).

Имя активного профиля меняется и сохраняется до чтения целевой пары файлов.
Возвращаемые значения обоих Load игнорируются. Отсутствующий файл bindings
возвращает false, оставляя назначения предыдущего профиля; UI затем снимает
dirty и показывает новый профиль. Для попадания в список достаточно
`B.settings.ini`, наличие `B.bindings.ini` не требуется.

Сценарий: A имеет свои назначения, B представлен settings-файлом без bindings;
выбрать B. Получаются настройки B и назначения A. Последующее сохранение
может записать назначения A уже под именем B.

Доказательство: сохранение старых bindings при missing-файле воспроизведено
probe; игнорирование false и порядок commit установлены по коду UI.
Исправление: сначала загрузить и проверить оба файла во временную модель,
затем применить модель и записать active marker. Ошибка сохраняет профиль A.

### F-03 / P2 — Неудачное переключение не отменяет удаление активного профиля

Место: `keyboard_subpages.cpp:6447–6451`; ранние выходы из
`Global_ApplyActiveGlobalProfile` — 5923–5934.

Перед удалением активного профиля вызывается переход на Default. Функция
возвращает void и может выйти из-за ошибки сохранения предыдущего профиля
или active marker. Caller всё равно вызывает `GlobalProfiles_Delete(name)`.
При недоступном для записи базовом settings.ini, но доступных файлах
GlobalProfiles, удаление возможно, хотя активным в памяти осталось старое имя.
Последующий save способен создать удалённый профиль снова.

Доказательство: статическая ветка обработки ошибок; UI fault injection не
выполнялся. Исправление: возвращать результат переключения и удалять только
после подтверждённого перехода, проверяя фактическое active name.

### F-04 / P2 — Пустой или посторонний INI считается корректным bindings

Место: `profile_ini.cpp:292–312`. Аналогичная слабость проверки существования
есть в `settings_ini.cpp:322–327`.

Перед сбросом всех назначений проверяется только GetFileAttributes. Проверки
читаемости, типа содержимого, схемы и обязательной структуры нет. Пустой файл
успешно проходит загрузку и обнуляет назначения. Это отличается от F-02:
здесь сам loader возвращает неверный успех, поэтому проверки bool недостаточно.

Доказательство: probe — `empty: loaded=1 LX_plus=0` после LX_plus=7.
Исправление: validate-before-commit; поддерживать явно распознанные legacy
форматы, но отличать их от пустого/случайного/нечитаемого файла. Ошибка не
должна уничтожать текущую модель. Добавить load-side malformed tests.

### F-05 / P2 — Сохранение и чтение CSV имеют разные пределы

Место: `profile_ini.cpp:61` (MaskToCsvForPad), 137–156 (запись), 221–232 (чтение).

Writer сериализует весь поддерживаемый bitset, reader использует фиксированные
2048 wchar и не обнаруживает усечение GetPrivateProfileStringW. Допустимый
длинный список сохраняется полностью, но загружается частично; после нового
save хвост теряется. Обрезка посреди числа может также исказить последний код.

Доказательство: список всех поддерживаемых кодов 1..1033 загружается с true,
но остаются только 539 назначений, код 1033 отсутствует. Это граничный случай,
а не утверждение, что обычная небольшая раскладка обязательно достигает лимита.
Исправление: динамическое чтение с обнаружением truncation и проверка round-trip
для полного разрешённого домена, включая границу посреди токена.

### F-06 / P2 — Число из INI обрезается до uint16 до проверки диапазона

Место: `profile_ini.cpp:22–24`, использования — 260–272.

ReadU16 напрямую приводит GetPrivateProfileIntW к uint16_t. Например,
LX_Plus=65543 превращается в 7 — валидную совершенно другую клавишу. Последующая
проверка IsSupported в построителе XUSB уже не может обнаружить исходную ошибку.
Затронуты оси и триггеры импортированных/повреждённых профилей.

Доказательство: probe — `numeric_65543: loaded=1 LX_plus=7`.
Исправление: строгий разбор целого в широком типе, проверка полного токена и
поддерживаемого диапазона до narrowing; 0 обрабатывать как отсутствие binding.

### F-07 / P2 — Профиль публикуется realtime-потоку по частям

Место: `keyboard_subpages.cpp:5937–5938`; `profile_ini.cpp:236–312`;
`settings_ini.cpp:239–241`; `backend.cpp:2026–2055`; `bindings.cpp:36–137`.

Загрузка сначала меняет живые настройки, очищает key settings и bindings,
затем восстанавливает назначения отдельными atomic store/fetch_or. Realtime
продолжает читать оси, триггеры и маски независимо. Отдельные atomics исключают
data race соответствующих полей, но не дают единого снимка всего профиля.

Возможное чередование: при удерживаемой клавише reader читает уже очищенную
ось до её восстановления; либо берёт новые curves со старыми bindings. В
игру может уйти промежуточное отпускание или смешанный report даже при переходе
между одинаковыми назначениями. Учитывая чтение INI внутри процесса загрузки,
это окно не ограничено одной атомарной операцией.

Доказательство: статическое чередование потоков, физический артефакт в игре
не измерялся. Исправление: целиком подготовленный immutable configuration
snapshot и одна публикация generation; один tick читает одну generation.

### F-08 / P2 — Два файла одного профиля не составляют одну транзакцию

Место: `keyboard_subpages.cpp:5921–5926`, 6334–6339, 6477–6480.

SettingsIni_SaveProfile и Profile_SaveIni по отдельности атомарны, но пишутся
последовательно. Если settings уже заменён, а запись bindings не удалась,
ранний return не восстанавливает settings. На диске остаётся смесь нового
состояния settings и старых bindings. Dirty/сообщение об ошибке не восстанавливают
согласованность после закрытия или аварии процесса.

Доказательство: статический сценарий failure второго commit; существующий
SaveTransaction тестирует одиночный adapter и не доказывает общую атомарность
пары. Исправление: профиль одним документом либо versioned pair с единым
атомарным manifest/commit marker и recovery. Нужна fault matrix между файлами.

## Дополнительные риски и несогласованности

Эти пункты не входят в число восьми воспроизведённых/установленных дефектов.

1. Output producer hang: `vigem_output_process_host.cpp:400–409` на timeout
   продолжает heartbeat, сохраняя последний report; heartbeat увеличивает
   progressSequence (`vigem_output_channel.cpp:506–515`), используемый supervisor.
   UI watchdog в `app.cpp:1344` проверяет жизнь realtime thread, а не возраст
   его публикации. При зависшем, но живом producer возможен stale nonzero output.
   Нужен targeted stall oracle с ненулевым report и живым parent; физически
   этот сценарий здесь не воспроизводился. Живость child не равна свежести input.
2. AULA Hero84 HE входит в обычный каталог (`native_analog_backends.def:11`)
   и обычную компиляцию (`HallJoy.vcxproj:465–466`). Текущая документация уже
   помечает отсутствие закрытой release-scope/physical gate. Это подтверждённое
   незакрытое release-замечание, а не новое доказательство ошибки протокола.
3. Корневой HallJoy.exe датирован 22 августа, build/output/HallJoy.exe —
   5 сентября; исходная версия по-прежнему 1.4.1.0. Без Git metadata и явного
   выбора артефакта легко тестировать другой EXE. Нужны source identity и hash
   выбранного release; свежесть одного output не переносится на корневой EXE.
4. Большой набор зелёных статических контрактов не покрыл реальные loader
   сценарии выше. Добавлять следует production-linked load/round-trip/fault
   tests, а не только проверку наличия нужных строк в исходнике.
